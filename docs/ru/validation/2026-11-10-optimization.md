# Диагностика, измерения и статус оптимизации

`diagnostics` возвращает снимок накопительных счётчиков через бинарный FLCP.
Текстовые primary и secondary USB Serial/JTAG consoles отключены. CMake отвергает
обе конфликтующие настройки, включая старый локальный `sdkconfig`. ROM/bootloader
при перезапуске рассматриваются отдельно от бинарного канала приложения.

Свежая конфигурация ESP-IDF 6.1.0 сравнивалась с локальной 10 ноября 2026 года.
Различались только `ESP_CONSOLE_SECONDARY_NONE`,
`ESP_CONSOLE_SECONDARY_USB_SERIAL_JTAG` и производный
`ESP_CONSOLE_USB_SERIAL_JTAG_ENABLED`. Локальный файл исправлен и пересоздан IDF;
остальные параметры не подменялись.

Исходный read-only USB-снимок физической Spark S3: установленная сборка
`657ded42eb48132ec693f4e4d36b910f3a19a2da489f5fc000a9214e75c69346`,
capabilities 127, активны `system.clock/main`. Сборка не была заменена при снятии
этого снимка. Максимумы относятся ко всему времени её работы, продолжительность
предыдущих сценариев неизвестна.

| Показатель | Исходное значение |
|---|---:|
| Internal free | 212047 байт |
| Internal minimum | 207059 байт |
| Largest internal block | 139264 байт |
| PSRAM free | 1959796 байт |
| Main task stack watermark | 27008 байт |
| Max runtime tick | 49 мкс |
| Max frame (сцена + display) | 189878 мкс |
| Lua used / peak | 0 / 0 байт |

Это исходная точка, не доказательство выигрыша новой прошивки и не полный пик RAM.
Ток, ошибки display/recovery, Lua, установка под нагрузкой и BLE требуют отдельных
аппаратных сценариев. Стек и BLE-пулы на основании одного снимка не уменьшаются.

Новая диагностика разделяет request, runtime logic tick, scene, resource reads,
rasterization (включая resource I/O), копирование DMA-строк и SPI. Длительности
могут включать вложенные фазы; их нельзя суммировать. Счётчики USB TX означают
байты, принятые драйвером, BLE TX — байты, принятые NimBLE, а не доставку приложению
компьютера. `usb_read_empty_wakes` — пробуждения по deadline без notification;
счётчики notification объединяют совпавшие причины, не считают каждый IRQ.

`boot_snapshot_ready=1` означает, что снимок снят после инициализации Core и
завершения асинхронного старта BLE (либо диагностируемого отказа). Minimum/largest
heap и watermark нужно дополнительно снимать во время каждого стресс-сценария.
SDK ограничивает размер ответа, сохраняет приоритет Lua fault details и выставляет
`diagnostics_truncated=1`, если часть необязательных полей не поместилась.

USB RX/TX обслуживает аппаратный модуль `usb/usb_link.cpp` на владельце Core.
За проход: один запрос и до 256 RX/TX байт. Частичный TX сохраняется до завершения,
при backpressure задача ждёт callback драйвера. RX/TX и смена физической сессии
будят задачу notification; неизменившийся USB tick её не будит. Малый accessor
статуса соединения размещён в IRAM для tick hook. Не подключайте VFS/select как
второго владельца USB callback бинарного канала.

BLE будит владельца при RX, indication completion и смене соединения. Постоянного
20-мс maintenance больше нет: используются deadline pairing, повтор после ошибки
TX и deadline готового события. Core не вызывается из USB ISR или NimBLE callback.
Проверка install commit продолжается порциями по 4096 байт из Core::tick;
адаптер отправляет отложенный ответ целым кадром. Файловые metadata/durable writes
и recovery остаются синхронными; это не строгая wall-clock гарантия.

По умолчанию сборка использует закреплённый `platform/`. Для явной проверки
изменяемого SDK доступен `-DFLINT_PLATFORM_DIR=/absolute/path/to/IgniteSDK`; это
development override, не замена проверки закреплённого подмодуля перед интеграцией.

## Проверка RAM перед запуском

Допустимость пакета использует стабильный лимит профиля 48 KiB internal и установленную ёмкость PSRAM. Возможность запуска проверяется по текущим free/largest отдельно: резерв `CONFIG_FLINT_INTERNAL_MEMORY_RESERVE` (32 KiB по умолчанию) сохраняется для DMA, транспорта и recovery; `CONFIG_FLINT_PSRAM_MEMORY_RESERVE` — 8 KiB. Во время асинхронного запуска BLE дополнительно сохраняется 32 KiB. Baseline обязательных служб служит сравнением; запуск использует текущий largest block, в том числе после освобождения BLE. PSRAM не увеличивает internal-бюджет. Резервы консервативные, ещё не подтверждены полным аппаратным стрессом; BLE-пулы и стеки не уменьшались.

USB RX ring ограничен 4160 байтами: полный кадр MaxPayload=4096 плюс framing и пустой продолжаемый commit/close. Это увеличение с 2048 подтверждено потерями burst во время Lua/display: IDF отбрасывает RX при переполнении без callback ошибки. Клиент держит не более одного обычного запроса и одного пустого `install_commit`; неограниченный pipelining не поддерживается. Передача/парсинг по-прежнему ограничены 256 байтами за проход.

SOF-monitor IDF может кратко сообщить отсутствие USB после задержанных Flash/tick callbacks. OS подтверждает непрерывное отсутствие 20 мс по IRAM clock, не по числу tick callbacks. Подтверждённое отсутствие закрывает сессию и очищает driver buffers; hello и session_close немедленно разделяют логических клиентов. `usb_sof_glitches` считает подавленные короткие провалы; `usb_rx_capacity_bytes` показывает резерв ring. Прямого счётчика потерь внутреннего ring публичный драйвер IDF не предоставляет.

## Display: контролируемое сравнение полос

На Spark, SDK b318eaa, 80 MHz SPI, BLE advertising, 20 чередований launcher/clock (40 полных кадров 280×240, 2688000 пикселей), строки сравнивались с полосами по две строки:

| На кадр | 1 строка | 2 строки |
|---|---:|---:|
| Pixel transfers | 240 | 120 |
| SPI | 27,037 мс | 20,429 мс |
| Copy | 10,609 мс | 10,551 мс |
| Paint | 20,606 мс | 20,613 мс |

SPI-время снизилось на 24,4%; сумма этих трёх измерений — примерно на 11,4%. Это отдельный контролируемый прогон, а не сравнение с неизвестной историей исходной прошивки. Ошибок display и сбросов USB-сессии в обоих прогонах нет. `display_pixels`, `display_transfers`, `copy_total_us`, `spi_total_us` позволяют повторить сравнение по разности снимков; `paint_total_us` поступает из SDK. Счётчики относятся к displayScene, без начальной заливки/recovery.

DMA stripe — 1120 байт, занимает прежний union с предыдущей Scene; static_assert сохраняет полный размер scratch. Драйвер принимает максимум две строки и завершает transfer синхронно до повторного использования буфера. Нечётная последняя строка и clipping проверены сравнением GRAM с SDK renderer, SPI faults — host recovery-тестами. Полный framebuffer сохранён; новые glyph caches/dirty-region sets без измерений не вводились. Физические tearing/ориентация требуют визуальной проверки.

## Финальные RAM, Lua и размер образа

Бюджет запуска использует текущие free/largest, а baseline хранится только для сравнения. Перед включением BLE дополнительно сохраняется ещё не использованная часть объявленного internal-бюджета активного приложения; worker не обращается к Runtime, эту проверку выполняет владелец Core. На плате со сборкой `CONFIG_SPIRAM=n` проверено: часы/display/USB работают, временный отказ Lua при включённом BLE не скрывает корректный установленный пакет, выключение радио позволяет запустить Lua, а включение радио не отбирает зарезервированную память приложения. После остановки приложения BLE снова включается. Это тест отсутствия доступной PSRAM, не физическая инъекция неисправности чипа.

Профиль теперь задаёт `CONFIG_SPIRAM_IGNORE_NOTFOUND=y`: отсутствие/ошибка инициализации внешней RAM допускает internal-only startup; ошибка включённого memory test по-прежнему вызывает abort в IDF. `.bss`/`.noinit` в PSRAM не размещаются. `CONFIG_ESP_TIMER_IN_IRAM=y` обязателен для USB observer во время Flash writes; неверная конфигурация отклоняется CMake. После обновления выполнить `idf.py reconfigure build`.

SDK reserve по bounded header удерживает до 4116 байт для максимального кадра вместо геометрического роста до 8192; `usb_parser_capacity_bytes` показывает фактическую ёмкость. Строковый разбор BLE peer address использует фиксированный формат, без scanf и без изменения порядка байтов. `gmtime_r` с числовым formatter сохраняет прежние `HH:MM` и `DD.MM.YYYY`; проверены UTC offsets, границы дня/года и високосная дата. Образ до этой оптимизации — 742208 байт, после неё и финальной настройки fallback — 732912 байт, уменьшение 9296 байт. Слот остаётся 1 MiB; таблица разделов не менялась.

Map-анализ: fonts.cpp около 78844 байт; Lua VM около 14929 байт. Приписанные stdio около 57 KiB включают объединённый linker pool строк — сама object-section `esp_stdio_register.str1.1` занимает 75 байт. Удалять диагностику по такой атрибуции нельзя. Изменений assertions, Lua instruction limits, GC и защитных проверок ради размера нет.

Изолированный host-профиль Lua 5.4.9: Windows, MinGW 13, Release library, heap cap 32768, медиана семи серий по 3000 вызовов. Для 1000 итераций целочисленного цикла без hook — 3,756 µs/вызов, с эквивалентным production count-hook (каждая инструкция) — 17,937 µs. Для 100 временных таблиц штатный GC — 10,845 µs/вызов и peak 11406 байт; принудительная полная сборка после каждого вызова — 11,711 µs, из них GC 3,422 µs, peak 17646. Это профиль изолированного VM workload на ПК, не значения ESP32 и не предложение отключить hook/GC. На Spark тестовый Lua counter показал logic max 578 µs и heap used/peak 5384/5422 байт. Частота hook и политика GC сохранены.

Аппаратная проверка пакета 717395 байт прошла с chunk payload до MaxPayload=4096: логическое закрытие до публикации отменяет проверку, resume сохраняет загрузку; во время commit проходили 80–82 info и запросы сцен, Lua обновлялся. Проверка заняла 3,65–4,51 с в отдельных прогонах. Максимальный шаг достигал 625312 µs: durable metadata/Flash/GC остаются синхронными, строгая wall-clock граница пока не обеспечена. После тестов пакет удалён и заводские часы восстановлены. В 10 прогретых BLE start/stop циклах с Lua largest internal block сохранялся на 102400 байтах; PSRAM оставалась стабильной. Это пики конкретных сценариев, не доказательство вместимости любого приложения.

## Питание и границы проверки

Ток не измерялся: измерителя/датчика тока нет. Изменения `ble_enabled` и устранение периодических пробуждений подтверждают поведение, но не дают численного выигрыша автономности. В текущем профиле CPU 160 MHz, FreeRTOS 1000 Hz; PM, BLE modem sleep и automatic Light-sleep не включены. По ESP-IDF 6.1 DFS требует проверки SPI/APB locks и временных ограничений, automatic Light-sleep — tickless idle и корректных wake sources. Подключённый USB Serial/JTAG требует политики PM lock/USB recovery; нельзя включать сон, теряя единственный способ вернуть выключенный BLE. Частота tick, PM и modem sleep не менялись без измерений.

Encrypted BLE, повторное сопряжение и сохранность существующего bond после deinit/start будут проверены пользователем на другом ноутбуке с Bluetooth; задача и контекст вынесены в TODO корня экосистемы. На текущем ПК Bluetooth-адаптер не обнаружен. Проверки Linux-сборки/BlueZ, визуальных tearing/ориентации, отключения питания во время commit/checkpoint и реальной неисправности PSRAM здесь не выполнены. Host SPI faults и модель RAM без PSRAM их не заменяют.

Проверены SDK CTest 14/14 с Lua и 8/8 без Lua; Flare CTest 17/17 (включая desktop_offline, preview_application_api, companion_sessions), OS pinned SDK 14/14, host 3/3, tooling unittest 2/2, firmware ESP-IDF 6.1 с PSRAM и без неё. Отдельная сборка Qt Creator с Qt 6.12/MinGW 13 также собрана и прошла 17/17. Общие форматы пакетов и ContractRevision не менялись, persistent BLE key по умолчанию включён; миграции разделов нет. Успех этих проверок не означает завершения перечисленных аппаратных проверок.


## Публикация продолжаемой установки

Закреплённый SDK делит публикацию install_commit на owner-thread шаги: проверка
proof, запись previous ref, перенос объекта и атомарная замена current ref.
Полный GC больше не выполняется в конце commit: до публикации он проходит по
одной записи каталога/паре ссылок за шаг с ограниченной памятью. Активный Runtime
продолжает работать до активации и сохраняется при ошибке durable publication.
Отзыв permissions выполняется отдельным шагом и не пишет grants.bin, если enabled
разрешений для пакета нет. Epoch checkpoint откладывается до окончания install.

Disconnect до публикации отменяет проверку с сохранением resume; после её начала
owner завершает публикацию и отбрасывает ответ отключённой сессии. После reconnect
обязательно перечитать каталог. install_publishing показывает эту границу,
install_publish_{count,total_us,max_us} отделяют время публикации от validation/GC.
Одна операция LittleFS/Flash остаётся синхронной; это не hard real-time гарантия.

Повторная проверка после разделения публикации (SDK a68abd4): образ 734096 байт,
build ID 2c324d3e0c8b2c0bf055ab8b110f092fa0bf6d9eb2a5e9b283c506aa28131724.
Два прогона пакета 717395 байт: commit 3,59/4,04 с, по 82 info плюс сцены,
Lua продолжал работу. Наблюдаемый максимум install_step 84,6–101,4 мс,
install_publish 53,5–67,6 мс; максимальная задержка info 111,5/139,3 мс.
USB disconnects=0, diagnostics_truncated=0, тестовые пакеты удалены.
Исторические 625 мс выше относятся к прежней цепочке финализации; состояние
Flash различается между прогонами, поэтому это не гарантированный коэффициент
ускорения и не worst-case deadline. Largest block после прогрева требует
отдельной нагрузочной BLE-проверки.

Повторяемый аппаратный USB-тест включён в tools/check_install_responsiveness.py:
`python tools/check_install_responsiveness.py --port <порт> --output <новый.json>`.
Требуются pyserial и зависимости compiler tools закреплённого SDK; тест меняет
устройство, временно ставит test.flint.installcheck, проверяет cancel/resume,
измеряет latency и восстанавливает прежнее приложение/удаляет пакет. Flare
должен освободить порт. Существующий JSON не перезаписывается. Это hardware-only
проверка, она не входит в автоматический CTest без устройства.

Третий прогон того же теста во время параллельной host/firmware сборки также
прошёл: commit 5,385 с, 96 info плюс сцены, максимум info 285,8 мс,
install_step 200,6 мс и install_publish 200,6 мс. Lua работал, USB disconnects=0,
diagnostics_truncated=0, cleanup завершён. Полные JSON всех трёх прогонов
сохранены; более медленный результат не исключается из оценки задержек.

При локальной проверке на Spark прошли 10 start/stop циклов: около 69 KiB internal освобождается в disabled; PSRAM не меняется, lifecycle errors=0. Это проверка памяти/связи, не измерение тока и не доказательство сохранности существующего bond при повторном pairing.
